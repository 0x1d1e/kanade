# Limitations

- niri only. Hyprland and Sway are not supported: focused-output routing, workspace changes and screen capture come from niri IPC.
- No screen reader support. Kanade draws with the GPU and builds no accessibility tree, so the island never registers on the AT-SPI bus and Orca cannot see it. Checked on niri with `Atspi.get_desktop(0)`: every other app is listed, Kanade is not. `kanade ui` (the `ui` Module) reads the same controls as a named tree for scripts, but it is not an AT-SPI tree and no screen reader reads it.
- A fullscreen window covers the island, Critical Activities like low battery and a pomodoro moving on to its next phase included; only the OSD and an open Surface show over it. The island sits on the Top layer, which niri draws below fullscreen windows; maximized and windowed-fullscreen windows do not cover it. See [ADR 0006](../adr/0006-island-on-top-layer.md) and [ADR 0021](../adr/0021-the-osd-returns-to-the-island.md).
- Files dropped on a Dock icon start the app with them only when its `.desktop` `Exec` has a `%f`, `%F`, `%u` or `%U` argument of its own and no `Path`; an app that takes one file at a time starts once per file, up to 8, and otherwise nothing starts and stderr says why. Paths go as they are, not as `file://` links.
- The Launcher closes as soon as an app is pressed, so an app that fails to start says why only on stderr, as the Dock's does.
- A Launcher command (`caffeine`, `screenshot area`, `lock`, `dictate` and the rest of its closed table) runs the Kanade verb of that name and waits for its answer before the island closes, up to 6 seconds; it takes no typed text, so a timed caffeine or a Do Not Disturb duration is the CLI's. A refusal shows on the row as `Not run: <why>`; an answer that is unclear or late shows `Not confirmed, may have run: <why>`, so check before pressing it again. The screenshot and recording-start commands close the island first and run a moment later, so a refusal then shows as a failed Activity. Dictation from the Launcher may only copy its text, as the focused window is unknown while the Launcher holds the keyboard.
- The Launcher calculator converts lengths, masses, volumes (US customary), areas, speeds, times, data sizes (`KB` is 1000 bytes, `KiB` 1024) and temperatures from a fixed table, and writes whole numbers up to 2^53 in hex, binary or octal. There is no currency, as that needs rates from the network, and no month or year, whose length varies. A `%` after a number is a percent, never a remainder. Sums show twelve significant digits, whole numbers below 1e15 in full.
- The Launcher shows emoji only from a color emoji font that holds them as pictures (CBDT or sbix), like Noto Color Emoji or Twemoji. Kanade's text draws only outlined letters, so it draws the font's picture instead; a COLR or SVG emoji font shows none, though copying still works.
- The charge limit needs UPower 1.90 or later and a battery whose driver supports charge thresholds; elsewhere its Controls tile does not show, and it is off by default (add `charge-limit` to `controls.tiles`) and `kanade battery limit` says it is unavailable. Kanade cannot set the threshold itself: UPower uses the one already set, or its default.
- Without `pactl`, `udevadm` or `dbus-monitor`, the OSD, notification Banners and battery reads poll instead of waiting for the system to announce a change, adding up to about 23 CPU wakeups a second at idle. A backlight changed by firmware without a kernel uevent shows no brightness OSD. See [ADR 0004](../adr/0004-wake-sources-on-announcements.md).
- Without `setpriv` from util-linux, helper processes like `pactl`, `udevadm`, `dbus-monitor` and `pw-dump` still work but may survive Kanade being killed abruptly. See [ADR 0004](../adr/0004-wake-sources-on-announcements.md).
- Screen recording records video only, the focused output whole, with `wf-recorder`'s `h264_vaapi` encoder; without a working VA-API driver it fails and the island says why. niri hands out a frame only when the screen changes, so a still screen records few frames. See [ADR 0013](../adr/0013-screen-recording-with-wf-recorder.md).
- Locking before sleep waits until niri says it holds the lock, which it says once every monitor on shows a lock screen; if it does not by logind's `InhibitDelayMaxSec`, sleep comes anyway and the lock shows on resume.
- An unlock sent just before sleep is asked over: the session unlocks for a moment, then locks again before sleep is let go, unless that outlasts logind's `InhibitDelayMaxSec`. Kanade sends the unlock under the same lock as sleep's gate, so only an unlock already sent races it. See [ADR 0025](../adr/0025-the-lock-screen-over-its-own-connection.md).
- The lock screen does not type the key that wakes monitors the `idle` Module powered off. It cannot know of monitors powered off any other way (`niri msg action power-off-monitors`, niri's own idle, the lid, a resume), so there the waking key is typed. When the monitors wake with no key here, the next key is dropped once. If niri does not deliver the waking key to the lock screen, a password typed within 250 ms of waking loses its first character.
- A PAM service that asks for anything but one hidden prompt (an echoed name, a second secret) fails every check: the password answers only the first hidden prompt. PAM's text and error messages show under the field, cut to 64 characters.
- With `lock.grace` above 0, any key, click, scroll or 4 px of pointer movement on the lock screen unlocks it without a password for that many seconds, only after a lock by the `idle` Module (never `kanade lock`, a lock before sleep or one asked again after a failure). Anyone at the keyboard in that window gets in.
- The session countdown's warning lists only what Kanade knows (a recording, a timer, live Activities) and logind's blocking `shutdown` inhibitors. It cannot know unsaved work in an app, and it is a warning only: nothing stops the restart, power off or log out. See [ADR 0077](../adr/0077-pre-flight-warnings-in-the-session-countdown.md).
- Caffeine's duration does not count time the machine is suspended. An idle daemon sees it only if it honors logind idle inhibitors; hypridle does, but one started while caffeine is already on misses it until it changes. The `idle` Module reads it directly.
- The `idle` Module honors logind idle inhibitors only while it can reach logind on the system bus. Without it, only caffeine and apps' Wayland idle inhibitors hold the stages, and caffeine turned off while the user stays idle counts again only from the next input or idle. See [ADR 0047](../adr/0047-idle-in-the-shell.md).
- The clipboard history leaves out only a copy its app marks sensitive with `x-kde-passwordManagerHint`, as `wl-copy --sensitive` does. A password copied without it is kept like any other copy until removed or cleared. See [ADR 0019](../adr/0019-clipboard-sensitive-content.md).
- The privacy cluster's microphone and camera see only capture that goes through PipeWire, using `pw-dump` from the `pipewire` package. An app that opens `/dev/video*` or ALSA directly, like `ffmpeg -f v4l2`, does not show. See [ADR 0003](../adr/0003-privacy-from-pipewire-graph.md).

- The `liquid-glass` finish copies the screen around each pane through niri's `wlr-screencopy`, for each pane's reflective edge, so it costs some GPU and CPU on every frame the screen behind changes. The glass is clear, with no blur (the `blur` finish is the one the compositor blurs, see below), and the edge reflects the screen around the pane rather than bending what lies under it, so text behind a pane shows through it. Over a bright page a pane darkens a little and then turns its ink dark, by the average brightness of the screen just around it, so over a page half bright and half dark either ink may be hard to read. `appearance.refraction` (off, experimental) makes the edge read inward, from the page under the pane, by taking Kanade's own drawing out of the copy; where that cannot be told (text, icons, the edge itself, or a frame that moved) it reflects as above. It costs a copy of each frame of the window, redraws while the page behind moves, and has not been looked at on a live session beyond the build and the rule's unit tests ([ADR 0100](../adr/0100-liquid-glass-unmixes-its-own-drawing.md)). The lock screen stays solid. See [ADR 0052](../adr/0052-liquid-glass-finish.md) and [ADR 0054](../adr/0054-liquid-glass-refinements.md).

- Inline reply (the KDE `inline-reply` action) works on Banners only, not in the Notifications Surface list. A click on the reply field gives the Banners window the keyboard until the Banner closes; Escape leaves the field, a click in another window returns the keyboard. Enter sends; the sender's submit button text is ignored. A reply is cut to 2000 characters, held in memory only and never logged. A Banner with text typed stays until sent or closed, and moving focus to another output while typing drops the text. Without the `banners` Module the capability is not advertised.
- The `blur` finish needs niri 26.04 or later (`ext-background-effect`); without it the panes are the opaque tinted solid, and `kanade doctor` says so. niri blurs only the wallpaper behind a layer unless your config has the layer rule in [Installation](Installation.md) (`xray false`), and calls the effect it then makes experimental. The compositor's blur has no rounded corners, so Kanade gives it rows of rects a pixel tall along each pane's outline. A Banner blurs once its fade in is over, and stops as it fades out. Its ramp follows `appearance.tone`, dark with light text or light with dark ink; there is no ink flip over a bright or dark window, the pane's fill alone keeps the text readable. See [ADR 0057](../adr/0057-blur-finish.md).
- A failed reload of niri's config (a parse error) shows on the Island for a few seconds as `niri config: Failed - run niri validate`, the failed form of a live Activity, so it needs the `live` Module on and says nothing more than that; niri's own message and `niri validate` say what is wrong. It also shows when Kanade starts or reconnects after the last load failed. See [ADR 0071](../adr/0071-failed-niri-config-as-a-failed-job.md).
- Banners show a notification's text on screencasts (a share, OBS) unless your niri config has the opt-in layer rule `block-out-from "screencast"` on `kanade-banners`, see [Installation](Installation.md). The rule covers Banners only: the Island holds the privacy dots, so the Notifications Surface, which draws on the Island, still shows on a screencast. A third-party screenshot tool is not covered by `"screencast"`. See [ADR 0070](../adr/0070-banners-out-of-screencasts.md).
- Changing what a share shows (`kanade capture cast`) works only for a cast with a dynamic target, which a portal share picks by its own choice, and needs a niri with the `set-dynamic-cast-*` actions (26.04 has them); there is no button for it in the Capture Surface or Controls, only the verb, which a bind can run. The Controls header marks casts `(paused)` when every one has stopped streaming frames, but only for a cast that captures a window or a screen. See [ADR 0072](../adr/0072-dynamic-cast-target-verb.md).
- Stop sharing in Controls ends only a PipeWire screen cast (a browser or chat app sharing through the portal), through niri's `stop-cast` action, so it needs a niri that has it. niri cannot stop a `wlr-screencopy` cast, like `wf-recorder`'s, so that one has no button; stop it in its own program or the Capture Surface.

- The Settings window is a normal window, so niri tiles it. To float it, add a niri window rule: `window-rule { match app-id="kanade" title="Kanade Settings"; open-floating true; }`.
- The lock screen's layout label shows only with two or more keyboard layouts, and follows what niri says; it can be stale for a moment after niri restarts. It shows no other state: no notification, media or battery.
- Settings' Health page shows what the checks found when it opened or Check again was pressed; it fixes nothing, so each warning says what to run. The first-start notice counts the checks 30 s after Kanade starts, so a service that starts later may be counted missing, and it is told only once, whatever the count.
- The `audio` visualizer follows the default sink as a whole, not one player, and needs `cava` built with PulseAudio support. It is untested against a live cava in this release; without cava the synthetic bars draw. See [ADR 0056](../adr/0056-audio-visualizer-through-cava.md).
- Synced lyrics (`media.lyrics`) show on the Media Surface only, not on the Island's Peek. A streaming player gives no file, so only `lrclib` can serve it, and only when it reports an album and a length. The `lrclib` lookup is untested against the live service in this release.
- The desktop's accessibility preferences come from the settings portal only (`appearance.accessibility`, [ADR 0080](../adr/0080-desktop-accessibility-from-the-settings-portal.md)): reduced motion and higher contrast, the latter only as a solid finish for the Island, Dock and Banners. It is untested against a live portal in this release. A file's `reduced_motion = false` does not override a desktop that asks for less motion.
- Moving an app to another output (the Route row in the Audio sub-surface, shown with two outputs) sets `target.object` in PipeWire's `default` metadata with `pw-metadata`, which WirePlumber honours. It is untested against a live PipeWire in this release, and the choice is WirePlumber's to keep or forget. See [ADR 0081](../adr/0081-per-app-output-routing.md).
- Brightness of an external monitor (`brightness.backend`) goes over DDC/CI, the monitor's I2C bus. It needs the `i2c-dev` module and write access to `/dev/i2c-*`, and some monitors or docks do not answer. A monitor's level is read once and kept, so its own buttons are not seen, and it can lag a new monitor by up to 10 s. One level is shown: that of the monitor under the focused output. It found no monitor on the NVIDIA card here, whose connector has no `ddc` link in `/sys/class/drm` (`ddcutil` reaches it); with the bus given, a read and a write worked on a Dell P1917S. See [ADR 0082](../adr/0082-ddc-ci-brightness-for-external-monitors.md).
- Apps' launcher entry progress (`launcher-entry` Module, the Unity `LauncherEntry` signal) shows as a live Activity titled with the app's name, at most 2 at once. Only `progress-visible` and `progress` are read: counts and the urgent flag are not shown. The signal is not authenticated, so any program on the session bus can claim to be an app; the name shown is the `.desktop` entry's, not the signal's. Few apps send it (Chromium and Firefox downloads, Nautilus, some others); it is untested against a live app in this release. See [ADR 0083](../adr/0083-launcher-entry-progress.md).
- Input methods (fcitx5, ibus) work in Kanade's text fields through the compositor's `text-input-v3`: composing text shows inline with an underline, the candidate popup sits at the caret, and commits go in at the cursor. A password field is told its purpose and nothing of its text, and the lock screen has no input method. Without that protocol, keys and xkb compose (dead keys) are all there is. A field never scrolls, so a caret past its right edge is placed at the edge. Untested against a live input method in this release. See [ADR 0090](../adr/0090-text-input-v3-in-the-runtime.md).
- `appearance.scale` (80% to 200%) scales the whole shell live, at the runtime's scale seam. A normal window already open (Settings) keeps its size and its content scales inside it, and the lock screen is not scaled. The Island's canvas is cut to the output as ever. Untested against a live session in this release. See [ADR 0091](../adr/0091-ui-scale-at-the-runtime-seam.md).
- The Calendar Surface changes and removes only the events it added (files in `$XDG_DATA_HOME/kanade/events`); every other event is read-only there, and nothing is written to Google, a vdir or a subscription. A change keeps what the file holds (a place, a reminder) but there is no way to type a repeat, a place, a reminder or a time zone, and a file with a repeat, several events or a zoned time, or an event that spans several days, ends on a later day, is timed with no end, has seconds in its time or is all-day with a title that starts like a time, is refused for change rather than cut to fit (it can still be removed, unless the file holds another UID's event too). A change or removal of an event whose file changed since it showed is refused (`Changed elsewhere`). A removal has no undo. See [ADR 0113](../adr/0113-owned-events-are-edited-in-place-and-keep-what-they-hold.md).
- `kanade ui` names the controls of the Island (hover, action pill), the Dock and its menu, the Launcher, every Surface (Controls with its Wi-Fi, Bluetooth and Sound sub-surfaces and arrange mode, Notifications, Tray, Session, Timer, Capture, Clipboard, Calendar, Media, Weather, Wallpapers, Keys), Banners, the Settings window (pages, switches, choices, steppers, list entries, Reset, Undo, Inspect, and a page's scroll area) and every text field. A name is the control's own (`wifi`, `back`, `clear`) or the key it sets in Settings (`dock.merge/switch`, `appearance.tone/dark`); the items of a list are `row`, `entry`, `card`, `picture` and the like, numbered (`row#2`) and renumbered as the list changes, since a network, device, app, title or file name is never a node's name (under `ui.describe = "content"` it shows as the node's content). Not covered: a control that takes a hold (the Clipboard's Clear) has a node, but `press` is a tap and does nothing, as does `key`; an owned Calendar event's `remove` button likewise takes a hold, so `press` on it removes nothing (its `edit` button is a plain press); what takes no click is described at most as a list or an event (the Keys' rows, the Weather's days) or not at all (a Bluetooth pairing code or PIN, which `key` can still answer); the Wi-Fi password field is a secret input that `type` can fill but `describe` never shows; the gesture overlay and the lock screen are never described. A slider is pressed at its middle. A control whose click is on a parent of what is named is reported covered. `ui` is refused while locked. `press` on a Bluetooth `pair` pill can accept a passkey confirmation without the code being readable from the tree (the code is never described); this is within the model that only you can reach the socket.
- The gesture launcher (`kanade gesture`) takes the pointer on the focused output only, with the grab held until the stroke ends, Escape, a right click, 8 seconds or a lock. It recognizes one stroke with the $1 recognizer: the stroke's start and direction matter (a circle drawn clockwise is not one drawn counterclockwise), a line drawn in any direction matches a line (turning is forgiven, so one gesture cannot be a line up and another a line across), and a gesture of several strokes is not supported. A stroke under 60 px long matches nothing. `gestures.<name>` is split on spaces with no quoting and runs only Kanade verbs; only verbs that act on the shell or the session's state are accepted; `ui` and any verb added later are refused, as are those that wait on you (`dmenu`, `capture color`), run a program (`activity run`, `activity hook`), or belong to a program's own Activity (`activity actions|pressed|wait`) or end the session (`session logout|reboot|poweroff`) are refused when the config is read. Your own commands go through [hooks](Configuration.md) or a verb. A verb that needs keyboard focus runs just after the overlay lets go of it, which is untested on every compositor setup.
- The buttons a program puts on a live Activity (`kanade activity actions`) are pointer-only and on Peek only: there is no Live Surface, so no key reaches them (`kanade ui press` does). On a 300 pt Peek the percent gives way and as many buttons as leave the title room are drawn, so a third may not show. Kanade runs nothing for a press; the program must read it back (`activity pressed` or `wait`). A press nobody reads waits (4 at most) until the Activity ends. `activity run` hears only a `cancel` action.
