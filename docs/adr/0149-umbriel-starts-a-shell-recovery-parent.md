# 149. Umbriel starts a shell recovery parent

Status: accepted. Amends ADRs 0018, 0025 and 0147 for Umbriel. niri's service and logind recovery path remain as before.

## Context

Umbriel's autostart forks and executes `kanade` once; its SIGCHLD handling reaps a dead shell without restarting it. Umbriel's source keeps an opaque blank screen when a lock client dies and accepts a replacement lock client, but does not set logind's `LockedHint`. Restarting Kanade without surviving lock intent therefore cannot restore its lock UI. The blank interval is source evidence; the live renderer-crash runs below observed the replacement lock, without capturing frames during that interval.

The startup owner must remain Umbriel: `dist/umbriel/config.toml` retains `autostart = ["kanade"]`. Moving ownership to systemd would change the requested session model.

## Decision

- Bare `kanade`, when Umbriel IPC is selected, becomes a non-rendering recovery parent before allocator, runtime and Modules initialization. It executes the same binary through a private child entry, with the compositor's environment inherited. Normal CLI verbs and native messaging do not enter recovery. niri still starts the shell directly under its existing service.
- The parent takes a nonblocking exclusive flock on `$XDG_RUNTIME_DIR/kanade-recovery.owner`. This empty file carries ownership only, no lock state; it is never unlinked, avoiding split ownership across inodes. The runtime's existing shell singleton stays separate. A reachable existing shell aborts recovery rather than creating a loop of rejected children. The parent is named `kanade-recover`; `pgrep -x kanade` continues to identify the renderer, and `kanade status` reports its parent PID. Doctor verifies that parent instead of requiring the niri unit under Umbriel.
- The parent binds to the UID/PID returned by `SO_PEERCRED` on the selected Umbriel IPC socket and holds a pidfd for its lifetime, rechecking the listener after opening it. PPID is not the compositor identity: Umbriel may spawn via another launcher or a transient scope. No new Wayland connection or renderer is added.
- There is one child at a time, reaped before replacement. Any child exit restarts after 250 ms, doubling to at most 8 s; a run of at least 30 s resets the delay. There is no restart-count limit that could strand a locked session. Spawn/setup errors are diagnosed and stop the parent. SIGTERM/SIGINT of the parent or compositor exit interrupts both child watching and restart delays. Shutdown sends the child SIGTERM, waits up to 6 s for its existing cleanup, then kills and reaps it. `scripts/dev` allows 7 s for the parent to finish. An abrupt parent death kills the child through `PR_SET_PDEATHSIG`.
- The private inherited socket pair carries only lock-intent bytes and acknowledgements. Its child endpoint is duplicated with close-on-exec and stdin is reset to `/dev/null`, so shell helpers cannot consume or inherit the channel. Before every compositor lock request, under the lock request mutex, the shell sends intent and waits for the parent to record and acknowledge it. Failure exits the shell before the compositor can receive an untracked lock request. The parent passes its retained intent to each replacement, which relocks before running the shell even with a false or absent logind hint. Logind remains a secondary startup source and remains authoritative for niri.
- Inherited lock intent is restored before ordinary Module activation can suppress it. If `module disable lock` was persisted while the old shell could still lock, the replacement starts only the connection and scenes needed to finish that lock, with lock verbs, sleep handling and lock/unlock hooks still off. On confirmed unlock or definite refusal/end, it first waits for the parent's clear acknowledgement, then exits; the next child has no inherited lock and leaves the disabled Module entirely cold. An enabled lock Module still starts once through its ordinary path; niri's Module behavior is unchanged.
- Intent persists through pending locks, a held lock, password acceptance and a queued unlock. The existing lock connection now issues `wl_display.sync` after `unlock_and_destroy` and reports `News::Unlocked` only on that callback. Flushing a request alone is insufficient confirmation. The shell clears intent only on this confirmation or definite `Finished` for its newest request. Older news and connection loss never clear newer intent.

## Verification

Disposable subprocess fixtures exercise actual process exit/restart, singleton refusal, a pre-existing shell socket, compositor PID death, parent termination and restart-delay cancellation, reaping, and acknowledged lock intent inherited by a replacement. Channel checks ensure a lock checkpoint waits for acknowledgement and rejects a closed parent channel. Lock request/state checks cover stale confirmations and the existing interleavings. A persisted Module configuration regression exercises disabled and enabled lock startup with and without inherited intent, using recording callbacks. Disposable child fixtures exercise the actual lock-news callback for confirmed unlock and refusal, checking that the child waits for the parent's clear acknowledgement before exiting. These fixtures include `News::Locked` and configured harmless commands: a disabled lock Module runs neither hook, while an enabled Module still runs lock then unlock.

Live **unlocked** Umbriel smoke on 2026-11-03 passed for candidate `e56d0fc`, binary `2e2f904e291f2314679c9d3cf6f67d4676aeb7a017eb0916cbc7884d4bcbbdcb`: killing only the renderer restarted it under the same recovery parent and compositor; status and UI remained responsive, doctor confirmed parent identity, duplicate startup was refused, and graceful parent stop reaped both processes. The original shell was restored afterwards. This remains evidence for that candidate's unlocked path.

The following observations are retained from the supplied Iris reports; the named temporary binary backup, config/state directories and screenshots were unavailable for reinspection during this documentation update. Two later live Umbriel runs used candidate `6ad11434ca099666dddf13ea32a519864503437d`, freshly built with `cargo build --locked`, binary SHA-256 `43e16923ee0834fa297dfec0f4aa7862912e1747bd7522cb140c77bd77f22e2b`:

- **Enabled lock Module** (Iris run `af57c72a0c2e4edde`): after a confirmed lock, SIGKILL of only the renderer produced a confirmed replacement lock under the same recovery parent and Umbriel. `kanade ui describe` refused with `session is locked`, and a screenshot showed the replacement lock screen while logind's `LockedHint` remained `no`. Authentication unlocked the replacement; the same parent survived and UI requests answered again.
- **Persisted-disabled lock Module** (Iris run `acaf26351fe6ea375`): `kanade module disable lock` persisted `lock = false` in temporary settings for the next startup. The current renderer still had the Module enabled, so its subsequent confirmed lock added one `lock` entry to a harmless hook marker. After one renderer SIGKILL, the replacement restored the inherited lock with the Module off under the same parent. UI requests refused with `session is locked`, a screenshot showed the lock screen, and logs reported restoration of the existing lock. The marker stayed at its single pre-crash entry through recovery and authentication: neither replacement lock nor unlock hook ran. After authentication, logs reported the recovered lock's end and restart with the Module disabled. The next child answered UI requests, refused the lock verb, reported the Module off, and left it cold; a screenshot showed the desktop.

In the disabled run, `kanade lock status` returned `module lock is off` (exit 1). The original live report labeled the whole run FAIL solely on that refusal. Source confirms it is expected: `src/modules/catalog.rs` parses both `lock` and `lock status` as verbs of the lock Module; `src/ipc.rs::answer` refuses verbs of an off Module before dispatch. `src/modules/mod.rs::activate` restores inherited lock scenes without turning that Module on. The refusal is a diagnostic limitation during recovery, not evidence that the inherited lock was lost. The observed replacement lock, input refusal, successful authentication and hook suppression establish those live results independently of that diagnostic.

Both runs used private config/state, left the real settings file's modification time unchanged, and gracefully stopped the parent after unlocking. Each restored the exact original shell binary, SHA-256 `60d961871d79b5dfde81068101103fd8d06a9106ce721288d96edab03ebd9b38`, directly under the same Umbriel, unlocked and responsive at the end of that run. These are historical observations, not a claim about the current session.

Neither run captured frames in the subsecond gap between renderer death and replacement. After-replacement screenshots establish that the lock UI returned; they do not prove continuous privacy or the no-desktop-flash invariant. That invariant remains **unobserved**. Live logout/compositor shutdown and niri acceptance remain **NOT RUN**. Compositor-death, parent-termination and restart-delay fixtures substantiate automated process-lifetime behavior only. The niri bypass is source-traced: `src/main.rs` continues into normal shell startup when `src/recovery.rs::start` returns `None` for a non-Umbriel compositor; this is not live niri acceptance.

## Limits

The parent itself is not supervised. Killing it abruptly or a parent failure ends automatic recovery and loses in-memory intent. Umbriel remains fail-closed on its blank lock screen after a locker dies; starting a new parent cannot infer the old lock without `LockedHint`. Recover from a TTY with a compatible replacement locker or end the graphical session as a last resort (unsaved work is lost). Do not intentionally stop the recovery parent while locked expecting a new parent to restore its UI.

A hung child is not detected; this is process-exit recovery, with no heartbeat watchdog. A crash loop continues at the capped delay. An ambiguous crash after a successful unlock but before the parent clears intent can conservatively relock. There are no passwords and no lock-state files in the recovery protocol.
