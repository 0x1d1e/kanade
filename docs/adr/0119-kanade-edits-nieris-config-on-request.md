# 119. Kanade edits niri's `config.kdl` on request

Status: accepted. Supersedes the statement "Kanade never edits niri's config" of [ADR 0057](0057-blur-finish.md) and [ADR 0070](0070-banners-out-of-screencasts.md) for an explicit, opt-in editor (below); the rest of both stands. Builds on [ADR 0041](0041-wallpaper-colors-in-apps.md) (appearance sync already adds one `include` line to this file) and [ADR 0071](0071-failed-niri-config-as-a-failed-job.md) (a failed niri load as a failed Activity).

## Context

niri's settings (gaps, focus ring, keyboard layout, `prefer-no-csd`, the screenshot path) live in one KDL file the user also edits by hand. A settings editor for it must not lose comments, formatting, `/-` slashdash, or a change the user's editor saved a moment before; must not make a config niri rejects; and must let the user go back. Mutating the `kdl` crate's tree is not that: it silently drops value edits and moves comments at the end of a file (reproduced), and no formatter rewrite keeps a hand-written file as it was.

niri 26.04 reads KDL v1 only. `niri validate -c <file>` takes about 10 ms, prints miette errors with color to stderr, and exits non-zero on error; it resolves relative `include`s from the validated file's directory.

## Decision

Slice 1 of the editor: the text engine and the CLI `kanade niri-config validate|get|set|remove|undo|backups|restore` (`src/niri_config.rs`). It runs in the CLI process, with no shell. The Settings page, reload confirmation (`ConfigLoaded`) and a symlinked config are later slices.

- **Edits are byte splices.** The `kdl` crate (feature `span` only, no new dependency) parses KDL v1 to find the byte range of a node and its value; the replacement text is spliced into the original string. Everything outside the range stays byte for byte: comments, `/-`, blank lines, CRLF, a last line with no newline. Text written is v1. A leading byte order mark is kept where it is. The result is parsed again and compared with the original node by node: only the intended node may differ.
- **Paths** are dotted node names to a single-valued node or flag (`layout.gaps`, `layout.focus-ring.off`, `input.keyboard.xkb.layout`, `prefer-no-csd`). A missing node is made at the end of its parent block, a missing block at the end of the file (before the appearance sync's closing include), with the file's own indent and line ending. A node removed takes its own line only (its text and a trailing `//` comment); a comment on a line of its own, directly above it or not, is never taken. Repeated nodes (`window-rule`, `spawn-at-startup`, `output`), blocks, nodes with several values and anything under `/-` are refused.
- **Only `config.kdl`'s own nodes.** Includes are followed as the Keys Surface does (loop and depth guards, `optional=true`). A node that any included file sets, before or after the config's own definition or alone, is refused with the file that owns it (an include before the config's own could be edited without being overridden, but the refusal is the safe rule and is kept for now); `appearance.sync`'s `kanade.kdl` colors are such. A node under `/-` is neither edited nor made again beside it.
- **Safety flow.** Refuse a symlink, a file not the user's, an unwritable directory, `/etc/niri/config.kdl` (the message tells how to make a user config from it). Snapshot the file (mtime, length, SHA-256). `set` and `remove` run `niri validate` on the original first and are refused if niri rejects it (a v2 syntax and a missing required include included); `undo` and `restore` do not, as a broken config is when they are needed, and need only the result to validate. A hard-linked file (more than one name) is refused like a symlink. The candidate is staged in a hidden file in the same directory with the original's mode, flushed (`atomic::stage`), and validated there; a rejection deletes it, changes nothing and shows niri's first error line with file:line:col. The backup is made, the target is read and hashed again, and the rename happens only if it still equals the snapshot (else 'config changed on disk'). niri's own exit code decides, and `Error:` in its output is a failure whatever the code.
- **Mutations serialize per config.** Every `set`, `remove`, batch `apply`, output edit, `undo` and `restore` takes an advisory exclusive `flock` before reading the file, selecting a backup, validating, staging a backup or committing. The lock file is in the private state directory and is named from the canonical config path, so processes editing the same target share it while different configs do not. The lock is held through the final snapshot check and commit. Editors that do not take this lock are still caught by that snapshot check.
- **Backups** in `$XDG_STATE_HOME/kanade/niri-config/` (directory 0700, files 0600): `config.kdl.<key>.<unix-ms>.bak`, the newest 20, and one `config.kdl.<key>.orig` of the first bytes Kanade saw, never rotated; `<key>` is eight hex digits of the SHA-256 of the config's canonical absolute path, so configs sharing a file name have rings of their own, and a backup of another key is refused. `undo` puts back the bytes before the last change, valid only while the file's hash is what that change left; `restore <n>|orig` puts any backup back; both pass the same staging, validation of the result and hash check, and keep what they replace as a backup.
- The editor is opt-in: Kanade changes the file only when the user runs a verb (and later presses a control) that says so. Nothing in the shell writes it by itself, except `appearance.sync`'s one include line as before.

## Consequences

- The wording "Kanade never edits niri's config" no longer stands. `dist/niri/config.kdl` and the wiki still show the rules a user may add; a later slice can offer them.
- Kanade processes serialize edits to the same config. Between the last hash check and rename, an external editor that does not take Kanade's lock can still replace the file (microseconds). `appearance.sync` writes the same file without that check (ADR 0041).
- A symlinked config (dotfile managers, Nix) is read-only here; a slice can follow the link within a managed directory.
- The flag list (`off`, `tap`, `prefer-no-csd`, ...) is Kanade's own; a node not on it is written with a value (`name true`), and niri's validation refuses a wrong shape.
- Changes to `spawn-at-startup` and `environment` take effect only when niri restarts; later slices say so.
- Settings' niri page (slice 2) is the engine's second caller. The engine gained `apply` (several settings in one change, one backup, one `undo`, all or nothing: turning a focus ring on can need `on` set and `off` removed), `read` (a typed `Reading`: unset, the config's own value, or an include's) and `editable`; the safety flow is unchanged. A worker thread runs the engine off the draw thread, one job at a time.
- A page switch for a flag is off by removing the node, except the border: niri 26.04 reads a `layout { border { ... } }` block in the top-level config with neither `on` nor `off` as on (not so in an include), so the page writes `off` to turn it off, and shows a bare block in `config.kdl` itself as on (`Editor::sets_in_config`). The focus ring (on by default) and the shadow (off by default) are not read that way.
- The page offers a fixed table of options (`src/settings/niri.rs`), each checked against niri 26.04's `niri validate` over the range the page keeps to; mouse `tap`, `dwt` and `click-method` are left out as niri rejects them. The page's Undo is the engine's `undo`, offered after a change in the window; the pinned original stays reachable by the CLI only.
- niri applies the file itself and keeps its old config if it rejects it; the page did not confirm the reload (slice 4, now amended below).

### Amendment: `output` blocks (outputs slice 1, engine only)

niri reads `output "<name>"` blocks repeated and multipart: it uses the first whose name matches the monitor (`OutputName::matches`: the connector, or `make model serial` with `Unknown` for what the EDID lacks, both case-insensitive), whole, and ignores the later ones. The engine therefore treats them apart from the repeated nodes it refuses:

- **Addressing.** A block is picked by its ordinal among the top-level `output` nodes of a file (`Block::Nth`), or is to be made (`Block::New(name)`). The same-looking blocks are told apart by that ordinal in the "only the intended node changed" comparison; a removed block shifts the ordinals after it, which the comparison allows for. A name is written as a KDL string (a raw string when it holds quotes or backslashes). `/-output "X"` blocks making a block only for the same `X`.
- **Resolution** (`OutputId`, `Editor::edit_output`). Blocks are read in file order with includes at their position. The first match is the block edited; the later matches are reported as shadowed. If any matching block lives in an include (`kanade.kdl` too), the edit is refused naming the file, as for any include-owned node: the include would keep or override what is set. With no match a block is made at the end of the file, before a trailing `include "kanade.kdl"`; its name is `make model serial` when all three are known (it then follows the monitor between ports) except for a built-in panel (`eDP-*`), named by its connector, and the connector otherwise. The CLI knows only the name typed, which it matches case-insensitively and uses for a new block.
- **Properties.** `Value::Props` gives a node with no arguments and no children its properties (`position x=1 y=2`, `variable-refresh-rate on-demand=true`, the bare node for `Props([])`). Each property the node already has is spliced where it stands and one it lacks is added at the end, so the file's own order, its spacing and the comments between its entries stay byte for byte (`position   x=0   y=0` becomes `position   x=-1920   y=0`); a dropped property goes with the blanks after it, or the ones before it when a comment stands in between. Property order carries no meaning in KDL (names are unique), so the round-trip check compares the set, not the order. A plain value Set on a node that has properties is refused, as it would drop them. `mode custom=true` and `modeline` are refused (Kanade does not edit what it does not offer), and so is a plain `mode` beside a `modeline`.
- **Names.** A block name holding a Unicode bidirectional control character (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) is refused at the write point, naming the code point: such a name could show as another monitor's, and the name of a monitor comes from its EDID. The CLI refuses it when it parses the name too, for its own message.
- **Reset** removes each key Kanade manages (`off`, `scale`, `transform`, `position`, `mode`, `variable-refresh-rate`) and then the block if it has nothing else in it (no other child, comment or properties); a block with `focus-at-startup`, `hot-corners` or a comment stays. A separator blank line a block was made with stays.
- `max-bpc` is in niri's current source but not in 26.04's parser (`niri validate` rejects it), so it is not managed.

The safety flow is the same: staged `niri validate`, backup ring, hash recheck, `undo`, and the refusals. The Settings Outputs section follows (next amendment).

### Amendment: the page's reload, undo and restart (slice 4)

- **Reload confirmation.** A change is written, then the page's worker waits for niri's `ConfigLoaded` (the counter `sources::niri::config_load_state`, as the Outputs section's Keep does) for up to 2 s and says in the footer whether niri reloaded the config, rejected it and kept the one it had, or has not said. The row stops saying Saving before the wait, so a slow reload never holds a control. When niri has reported no load at all since Kanade started (no niri listening), nothing is waited for and nothing is claimed.
- **Undo of this window's own change only.** The backup ring is shared with the CLI and records no window, so a change the CLI makes after the page's becomes the ring's newest and the engine's hash check passes for it. The page therefore keeps the hash its own change left (`Editor::last_change_hash`) and its `Undo` goes through `Editor::undo_only`, which refuses when the ring's newest after-hash is another's; the plain `undo` stays for the CLI. A later read whose stamp differs from the one the page's write left also takes the page's Undo away, so an out-of-band change is not offered as undoable. The engine's plain `undo` still undoes that change, which is right for the CLI.
- **Restart note.** `spawn-at-startup`, `spawn-sh-at-startup` and `environment` are read when niri starts. A written change to one says so in its message (`niri reads environment when it starts, so this applies after a restart`), and the page shows a standing note when the config sets one of them, since a change to it does not apply until then.
- **What a bare block means.** niri 26.04 applies bare-block-means-on in one place only: a `layout { border { } }` in the top-level config (`niri-config/src/lib.rs`, `recursion == 0`). `hot-corners` is value-read (a bare block turns no corner on; niri's own default top-left corner is not a block's doing), and `animations`, `tab-indicator` and `insert-hint` are presence-flag reads whose `*Part` holds `off` and `on`, so a bare block leaves niri's defaults standing. Nothing else needs the border's workaround.
- **The file's own shape.** A new top-level node goes at the start of a trailing include's line, so an indented include keeps its indent and no line is left holding only blanks. A new nested node takes the step its own block's children take, so a file mixing tabs and spaces gets no odd indent; the file-wide step is the fallback.
- **A part file left by a signal.** `atomic::sweep`, run on every staged write, removes the `.<name>.<pid>.<n>.part` files beside the file whose process is gone, which SIGINT or SIGTERM during `niri validate` used to leave. A live process's part, and this one's, are left alone.


### Amendment: the Outputs section (outputs slice 2)

The niri page gained an Outputs section: a card for each connected monitor with Enabled, Mode, Scale, Transform, Variable refresh rate (when niri says the monitor supports it) and Position. It differs from the page's other rows in that a wrong value can leave no picture, so a change is **tried before it is written**.

- **Live try.** A change runs `niri msg output <name> mode|scale|transform|vrr|on|off|position set ...`, which lasts only until niri reloads its config; the config is not touched. After about 300 ms the page asks the `Outputs` IPC request again and shows what niri applied. The IPC is the shell's own (`sources::niri::ask`); there is no new Wayland connection. The values sent come from what niri listed (a mode) or a range (a scale from 0.5 to 4), and niri's message on a rejection is shown as it is.
- **Confirm.** A footer bar asks Keep or Revert with 15 seconds on it, restarted by each further change; one monitor at a time. Keep writes the trial's changes through `Editor::edit_output` (one validated apply, one backup, and the footer's Undo), rewrites the pending file with `saved: true`, waits for niri's reload and compares, saying once if niri shows something else than the file now holds. A reload not seen in the window ends the trial with the file kept as a saved record.
- **Guards.** `niri msg output` takes a negative position only after `--` (`position set -- -1920 0`; clap has no `allow_hyphen_values`), in the trial and in the revert. A revert or recovery never turns off the last output that is on (a trial that turned B on, A since unplugged: B stays on, said once). A Mode trial on a custom mode is refused up front: `Previous` has no mode name to put back.
- **Revert** (the button, Esc, the time, the page or search being left, the window closing, Kanade exiting) puts back the `Previous` state: what the `Outputs` request reported before the first change of the trial, as a diff against what niri shows now, forcing the edited fields. It is not the config's: the file may not hold what the monitor showed. A failed revert keeps the trial and the pending file and is retried every 5 s.
- **Crash recovery.** `$XDG_STATE_HOME/kanade/outputs-pending.json` holds `Previous`, the time and the applied edits, written (atomically) before niri is told of the first change, and removed when the trial ends; Keep writes it again with `saved: true` once the config is written. A change is not made if the file cannot be written. At start a saved file is deleted without asking niri (the config holds the change); an unsaved one is applied and deleted, forcing the fields the applied edits touched, since niri's report cannot tell On from On demand. niri is asked up to five times, 2 s apart, as it may not be up. 5 minutes is the bound (our choice): a trial is over in 15 s, so an older file is from a Kanade that died and left the monitors to someone since, and applying it could undo their work. Past the bound the file is deleted unread **unless niri's live output still shows exactly the trial's applied edits**: then the trial is still on the monitor, so the output is put back to `Previous` before the file goes, and one that already shows `Previous` is deleted with nothing sent. The comparison is field by field against the edits the file records, so a monitor someone changed since is not mistaken for the trial's (`pending_file_older_than_five_minutes_restores_if_trial_state_is_live`). SIGTERM and SIGINT are caught (`clock::on_terminate`: a handler writes the signal to a pipe, a thread reads it, runs the revert for at most 3 s and ends the process by the same signal), so `systemctl --user restart kanade` and `scripts/dev` revert first, as does an exit that returns from `run()`. SIGKILL and a crash get no revert until the next start, and the 5-minute bound stays: a restart takes seconds, and a longer one is more likely someone's work than ours. A list with no output in it, or none at all, is niri not ready, not every output gone: the file stays and it is tried again.
- **Guards.** The last monitor that is on is not turned off (the only rule about that); a block an include owns, or a monitor with two matching blocks, is read-only and names the file; Position is both coordinates or none; a scale outside the range is refused. On-demand variable refresh rate is invisible in the IPC (niri reports it off until a window wants it), so the card takes it from the config.
- **Not here (slice 3):** the layout canvas, blocks of disconnected monitors, and `ConfigLoaded` as the confirmation that niri loaded the file (now a timed comparison with the IPC).

Files: `src/niri_config.rs`, `src/niri_config/` (`edit.rs`, `backup.rs`), `src/settings/niri.rs`, `src/settings/view/niri_page.rs`, `src/atomic.rs` (`stage`), `src/cli.rs`, `src/settings/outputs.rs` and `outputs/` (model, `Controller` with its `Port`, worker, tests), `src/settings/view/outputs_page.rs`, `src/main.rs` (recovery at start, revert at exit), `docs/wiki/CLI.md`, `docs/wiki/Settings.md`, `docs/wiki/Limitations.md`.

### Amendment: the page's changes are staged (batch 1a)

Changed of the slice 2 text above: a press no longer writes. A change to one of the page's options is staged in memory and written by Save, so "one validated write, one backup, one `undo`" holds of a Save, not of a press.

- **One write.** Save sends every staged change as one `Editor::apply`: one read, one `niri validate` of the original and of the result, one backup, one commit, one `undo`. The file's modification time advances once and `kanade niri-config backups` gains one entry, however many rows were changed. A Save whose every change the file already holds writes nothing and takes no backup. A row changed while that write is in flight keeps its newer change staged, since the file holds what was posted, not what the row now shows.
- **Only the config's own file.** The rule is unchanged: Kanade writes the config it was asked to edit and nothing else, so a node any include sets is refused with the file named, and a change splices one node's bytes with the comments, blank lines and line endings around it kept. Staging does not widen it: a row an include owns stages nothing to write, and a Save that meets one keeps every staged change and says why in the footer.
- **What a row shows.** A staged change is laid over the engine's `Reading` for its paths (the value that would be written, `Unset` for a node removed), so a row shows what Save would write, a staged Reset shows niri's default again, and `set`/`default` follow the staged state. A pending row says `Not saved` in the row itself, and `Saving…` while Save runs. No second copy of the file is kept.
- **The footer.** While anything is staged the footer offers Discard and Save in place of Undo, and its line says how many changes are not saved. Both are ring stops of the page's own keyboard (Tab and Shift+Tab, Enter or Space); no key is added. Save writes; Discard drops every staged change and reads the file again.
- **A failed Save.** A Save the engine refuses (niri rejects a value, the file changed on disk, an include owns a node) writes nothing, keeps every staged change and shows the engine's words in the footer. Undo is offered again only once a Save has written.
- **Leaving the page.** Closing the window discards what it staged, and the worker sees the window gone on its next poll; a window opening starts over (`State::reopen`) with the file read again, so a reopened page shows the file. Nothing is written either way.
- **Not staged.** The recommended-rule switches write at once, as before: a rule is a block the engine makes or removes whole, not one of the page's option paths. The Outputs section's trial, Keep, Revert and Reset keep their own flow, and a Keep is a validated write of its own.

Files: `src/settings/niri.rs`, `src/settings/view/niri_page.rs`, `src/settings/view.rs` (the footer's Discard and Save), `docs/wiki/Settings.md`, `docs/wiki/Keyboard.md`, `docs/wiki/CLI.md`.
