# 111. Voice dictation through the Gemini API

Status: accepted. Implemented (this document, the pure core, the state machine, the recorder, the Module, the `dictate` verbs, the Activity Kind, and inserting by copying, pasting or typing). Resolves the "ASR dictation" deferred decision in `docs/design.md`. Builds on ADR 0016 (secrets in the Secret Service), 0004 (wake sources) and the privacy cluster (the microphone indicator reads the PipeWire graph). Supersedes nothing.

## Context

Dictation turns speech into text where the user is typing. The user wants it without a local speech model and with the Gemini API, on the **free tier**. Google's terms for the free tier say, as the user understands them (not re-checked for this ADR), that content sent through it may be used to improve Google's products, and may be read by people. That is a privacy cost the user accepts, but the shell must say so before the first byte leaves, and never send without that acceptance.

## Decision

- **Dictation is a Module, `dictation`, off by default.** It starts no thread or helper while off (CONTEXT, Module).
- **The engine is the Gemini API, only.** Model `gemini-3.5-transcribe`, `POST https://generativelanguage.googleapis.com/v1beta/interactions`, the key in the `x-goog-api-key` header (never in the address, so never in an error that names the address). No local model.
- **One request after the recording stops.** The recording is kept in memory as 16 kHz mono signed 16-bit PCM, captured from a `pw-record` child (`--rate 16000 --channels 1 --format s16`, `-P application.name=Kanade`, writing to stdout), wrapped in a 44-byte WAV header and sent inline, base64, with `store: false`. It is never written to disk. It is capped at 120 s (3 840 000 bytes of PCM); the cap stops the recording and sends what was heard.
- **The privacy dot is not duplicated.** `pw-record` is a PipeWire client reading the microphone, so the privacy cluster already lights the microphone indicator from the graph, if the `privacy` Module is on and `privacy.indicators` is true. Dictation adds no indicator of its own; with those off, only its Activity shows.
- **The gate: a key and a consent, both.** Nothing records and nothing is sent unless both exist (`dictation::gate::decide`: `NoKey`, then `NoConsent`, else `Ready`).
  - The key is in the Secret Service (ADR 0016), item `application=kanade account=dictation-gemini`. It is not in the config, a state file, a log, `kanade status`, `kanade ui` output or an error message. Errors that carry the server's words cut the key out of them.
  - The consent is a marker, `$XDG_STATE_HOME/kanade/dictation-consent`, owner-only, whose text is the disclosure's version (`gemini-audio-disclosure v1`). Reword the disclosure materially and the version rises, so the old marker no longer counts.
  - The disclosure the user accepts says: the audio of each dictation is sent to Google's servers; the free tier's content may be used by Google to improve its products and may be reviewed by people, so nothing private, confidential or about other people should be dictated while on it; paid usage is under other terms the user should read, and Kanade cannot tell which kind of key it holds; the audio leaves the machine only after a dictation is started by the user, and is not kept by Kanade. The wiki page carries the same words.
- **Insertion**: `dictate.insert = "copy" | "paste" | "type"`, default `copy`, and `dictate.never_in`, a list of app ids. `dictation::insert::decide(mode, focus at start, focus now, never_in, tool available)` is pure, reads no clock, and answers `Type`, `Paste` or `Copy(reason)`. It answers `Copy` with a reason, in this order: the mode is `copy` (`Chosen`); either focus is unknown (`FocusUnknown`); the focused window is not the one the recording started in (`FocusMoved`, by niri's window id); its app id is in `never_in` (`NeverIn`, compared without case and without a `.desktop` suffix); `wtype` is not on the PATH (`NoTool`). A tool that runs and fails is the sixth, `ToolFailed`, found only after trying. Every copy but `Chosen` is marked sensitive.
  - The decision is made again right before the keys are sent (after the clipboard is set, for `paste`) and the dictation is checked to be still current at that moment too, so a cancel or a focus change in between is honored (a `paste` cancelled then still leaves the sensitive copy on the clipboard); but focus can still move between that check and the compositor acting on the keys (check-then-act), and a key already sent cannot be recalled. The guarantee is "the window in front was the one the dictation started in, a moment before", not an atomic one; `never_in` and `copy` are for text that must not leak.
  - The focus comes from the `Windows` service that niri.rs already feeds (no new niri connection): read when the recording starts and again when the text is ready. The text is not typed where the user did not start, as far as a check just before can tell.
  - `type` runs `wtype -`, with the text on its stdin (`wake::feed_within`), never in an argument and never in an error. The text is first made one line (whitespace runs, including line breaks and tabs, become one space, and every other control character, Escape, Ctrl-C, Ctrl-D, Backspace, Delete and NUL among them, becomes a space too): typed into a terminal a line break is Enter, and the model's words would run as a command.
  - `paste` puts the text on the clipboard as a sensitive copy, as the same one line without control characters that `type` types (so Ctrl+V cannot paste a line break or an escape into a terminal), then sends `wtype -M ctrl -k v -m ctrl`. The text stays on the clipboard afterwards, as it does for any paste. A terminal pastes with Ctrl+Shift+V, so `paste` does nothing, or the wrong thing, there; `type` is for terminals, and `never_in` is the way to keep the text out of one.
  - Sensitive means `wl-copy --sensitive`, which keeps the text out of clipboard managers that honor it. Older wl-clipboard rejects the option; the copy is then retried without it rather than lost, so on such a system the fallback is not hidden from a clipboard history.
  - **`never_in` is empty by default.** A built-in list would be a guess at which apps matter (password managers, terminals) that is wrong for some users and silently stale for others, and an unlisted app would look protected. What protects the user by default is that `copy` is the default and that a moved focus always falls back. The settings page and the wiki name the key, and the example is a password manager.
  - What was done is stated in the Activity (`Typed`, `Pasted`, `Copied`, or `Copied; <reason>`). The text is shown there, as before, and appears in no log or error.
- **Trigger**: `kanade dictate toggle`, bound to a niri key. The Activity Kind `Dictation` shows it: Ongoing with Stop and Cancel while it records, and Discard while it transcribes (the upload cannot be recalled after the stop, so the button only drops the result), then a Transient Actionable with the text or the failure. The key, the consent and the stop are in `kanade dictate key|consent|forget`, which run in the user's terminal and never reach the shell: the key comes by stdin, the consent is a typed phrase that needs a terminal.
- **Machine**: `dictation::machine` is pure and reads no clock; the seconds shown and the 120 s cap both count the audio bytes heard. Each recording has a serial, and an event for another is ignored, so a late answer never lands on a newer dictation. The gate is read on one long-lived gate thread, and the key is held in memory from the start of a recording to its request.
  - A toggle that starts moves the machine to `Gating { ticket }`, which refuses another toggle and ends on a cancel; the verdict (`Gated`) names its ticket, which becomes the recording's serial, so a verdict after a cancel is ignored and the key it read is dropped.
  - **The recorder starts on a thread that lives as long as Kanade.** `pw-record` runs under `setpriv --pdeathsig`, which fires when the thread that started it ends (ADR 0027, `wake::run`). The gate thread is started by the first toggle and kept; the recorder starts from it and from nowhere else a thread can end (the draw thread only stops it).
- **Copy**: `wl-copy` is fed the transcript on stdin (`clipboard::put_private`), not as an argument.
- **Failures are logged and show their status.** Every non-200 answer logs one stderr line, `kanade: dictation: Gemini answered <status>: <error.status> <error.message>`: the status string cut to 32 characters of `[A-Za-z0-9_-]`, the message with the key cut out (`redact`), whitespace collapsed and capped at 200 characters. A transport failure logs its kind only (`timeout`, `host not found`, `TLS error`, ...), never ureq's text, which can name a host. No header, request body, audio or key is logged. The Activity says "Gemini is unavailable (503); try again" and "Gemini refused the request (400)"; Google's words stay in the log, not on the island. There is no retry.
- **Status** (`kanade dictate status`) says how the dictation stands and the gate beside it (`ready`, `no key`, `no consent`), read on the gate thread from the existence of the key and the consent marker. The key is loaded as the gate always does and dropped; its value is never printed.
- **Consent is checked again before the audio is sent.** The request thread reads the marker once more immediately before `transcribe`; if it is gone or stale the dictation fails ("Consent withdrawn; nothing was sent") and the audio is dropped. `kanade dictate forget` also asks a running shell to cancel. An upload already begun cannot be recalled: after the stop, Cancel only discards the result, and the docs say so.
- **Not while locked (ADR 0025).** A start is refused while `lock::holds()`. Text is never typed or pasted into a locked session: `decide` answers `Copy(Locked)`, a sensitive copy, chosen over discarding so the words are not lost, and over typing, which would go to the lock screen. A recording under way when the lock comes is given up: the reader checks `lock::holds()` before each chunk of audio, and the machine (`Event::Locked`) fails a recording not yet stopped as "Cancelled: the session locked", has the recorder interrupted and drops the audio, so the microphone is not left open behind the lock screen. One already stopped is on its way and finishes; its text is then only copied.
- **Threads end the dictation.** The request, the insertion and the recorder reader run under a panic guard: a panic in one ends the dictation as Failed ("internal error"), never leaving it Transcribing.
- **Typing the key**: with a terminal, `dictate key` reads the key with echo, signals and line editing off (`stty`, the settings saved with `stty -g` and put back after), so Ctrl-C cancels it and the terminal is restored; a SIGTERM or SIGHUP during the prompt can still leave echo off.

## Unverified

No live key was available when this was written. None of the following has run against Google, and the docs and the user must not take it as fact:

- that `gemini-3.5-transcribe` takes **inline audio** in an Interactions request (rather than only an uploaded file);
- where `store: false` goes in the body (written as a top-level field);
- the field that holds the text of an answer (`outputs[]` text parts are read, else a `model_output` step's `content`). A first live run on about 24 s of quiet-room audio got HTTP 200 and an answer read as unreadable; the body was not seen. An answer that is JSON but holds no `outputs`/`steps` array, no `model_output` step or no text part is now reported as "No speech heard" (`Silence`), and `Unreadable` is kept for a body that is not JSON, not an object, or has a field of the wrong type. Either outcome logs to stderr, once per dictation, one line of names only: `kanade: dictation: no transcript: status 200, keys [..], step types [..]`. No value, header, request body, text or key is in it, and names are cut to 32 plain characters. The next live run with real speech shows the true shape;
- the fallbacks if real speech also fails, not tried because they would be guesses: an `Api-Revision: 2026-05-20` request header (other audio samples in Google's docs send it, those of the transcribe model send none), and `generation_config.transcription_config` (`language_codes`, `mode: "smart"`);
- whether a prompt part is wanted beside the audio (none is sent);
- whether a key restricted in Google Cloud to some API can call this one, and what 401 against 403 mean for it (both become "the key was refused");
- the free tier's quota and its 429 behavior;
- that `wtype` types into the focused window of the user's compositor and sends Ctrl+V as written (not run for this slice: a keymap change by `wtype` can race, and the first characters may be lost, as the key-sending notes in AGENTS.md describe for tests);
- that the recorder, started from the long-lived gate thread, survives between toggles in a live session (the structure follows ADR 0027; no stand-in test or live run covers it);
- that `lock::holds()` is true for the whole of a lock, from the first request to the unlock (read, not exercised with a dictation);
- that `wl-copy --sensitive` is honored by the clipboard managers in use;
- how `pw-record` behaves when its output is a pipe closed early (it is stopped with SIGINT, which was checked to end it with its audio intact, not against every PipeWire version).

The request body and the answer parser are each one function in `src/sources/dictation/api.rs`, with fixtures written from the documented shape in its tests, so a first run against a real key adjusts one place.

## Alternatives

**A local model (whisper.cpp and the like).** No data leaves, but it brings a model download, a native dependency or a helper, and accuracy and latency work. The user asked for the API only; deferred, not refused.

**Streaming (live partial text).** A realtime API would show words as they are said, and shorten the wait. It needs a WebSocket, a different model and protocol, partial-text insertion that is safe in an unknown window, and a held connection while the mic is open. One request after the end is simple and bounds what is sent; deferred.

**Writing the recording to a temporary file.** Simpler plumbing, but audio of the user's voice on disk. Refused.

**The key in the config.** Config is committed to dotfiles. Refused, as in ADR 0016.

**Consent implied by pasting a key.** The key says the user has an account, not that they read what the free tier does with audio. A separate recorded acceptance is the point.

## Consequences

- The first dictation needs two steps (key, consent) that the wiki page and the verbs' refusals both name.
- With the free tier, every dictated word may be used by Google. The only protection is the disclosure and the user's choice not to dictate secrets.
- A transcript is the model's reading, and can be wrong, or empty for silence; it is inserted as it came, with no editing except that typing flattens it to one line.
- A network failure loses the recording (it was in memory, and the request is the only copy). A retry from memory within the same Activity is possible later; it is not decided here.
