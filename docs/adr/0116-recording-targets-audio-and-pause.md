# 116. Recording targets, audio and pause

Status: accepted (Capture, slice 1); the window target it left out is [ADR 0117](0117-window-recording-through-nirs-screen-cast.md). Supersedes in part [ADR 0013](0013-screen-recording-with-wf-recorder.md): the recording is no longer only the focused output, without sound and in one piece, and `start` answers once the first frame is written, not at once. The rest of 0013 stands (`wf-recorder` through wlr-screencopy, the holder dying by SIGINT, the Activity's lifetimes); its `h264_vaapi` and no fallback encoder are superseded by the Update below. Builds on ADR 0011 (holders) and ADR 0112 (the Launcher's closed verbs).

## Context

Recording was the focused output whole, video only, start and stop. Capture is meant to cover an area, sound and pausing too. Window recording is not in this slice: niri gives no usable rectangle for a tiled window (its layout is scrolling, a window's place on screen is not in its IPC), so a window needs a PipeWire cast of the window itself, a different pipeline from `wf-recorder` and its own decision.

## Decision

- **Targets.** `screen` (the focused output, as before) or `area`. An area is one rectangle in layout coordinates, `x,y WxH`, from `slurp -d -f "%x,%y %wx%h"` run by Kanade, or given in the verb (`capture record start area 100,200 800x600`). Each side is rounded down to an even number (VA-API's chroma planes are half size); a side left under 2, or over 16384, is refused. `wf-recorder -g` finds the output the area lies on. Leaving `slurp` with Escape records nothing and is no failure; `slurp` failing (missing, or ending with an error) is one, and shows as a Failed Activity. Cancelling the picker (Stop or a lock while it runs; Pause is refused as "not recording") ends `slurp` with SIGTERM, as it inherits Kanade's ignored SIGINT, and one picker runs at a time (the worker thread is held until it ends).
- **Audio is one of `none` (the default), `system`, `mic` or `both` (`mix`).** `system` is `--audio=@DEFAULT_MONITOR@` and `mic` is `--audio=@DEFAULT_SOURCE@`. `both` (`mix`) captures system audio and microphone simultaneously using a virtual PulseAudio/PipeWire null sink (`kanade-record-mix`) and loopback modules routing default monitor and default source into it (the recorder reads `--audio=kanade-record-mix.monitor`, window muxer `-i kanade-record-mix.monitor`). The microphone is an explicit choice for each start (including `both`/`mix`): no config key, no saved setting, no Launcher command (the Launcher refuses `mic` and `both`/`mix` starts, ADR 0112's `denied`). The Capture Surface keeps the last choice in memory only, so it is `none` again after a restart. The Activity says what it hears ("microphone", "system audio", or "system audio + microphone") while it records. A runtime ledger `pulse-mix.<pid>` tracks module IDs; stopped or aborted takes unload them and remove the file; shell startup reclaims stale ledgers and lingering mix modules.
- **A state machine, pure.** `Idle`, `Picking`, `Running` (a segment, with a pause or a stop asked for), `Paused` and `Joining`, in `src/sources/recording/machine.rs`. Events (start, pause, resume, stop, lock, the picked area, a spawn, a segment's end, the join's end) give effects (pick, cancel, spawn, interrupt, join, post an Activity); it reads no clock and runs nothing. Each child has a serial, so the end of a segment or a pick that was already replaced is dropped. Pause is refused before the first frame (there is nothing to keep), and a stop asked while pausing wins and saves. A recorder interrupted by SIGINT before it had a handler, with no frame written, is an empty segment too, and a segment whose start comes after a stop or a lock was queued is never started (nothing records after a lock, the microphone included).
- **Pause is segments.** `wf-recorder` has no pause that keeps the file whole and still is a cast; pausing stops it with SIGINT (finishing a playable mp4) and resuming starts a new one. The first segment is written straight to the final file, so a recording never paused is that file from its first frame and needs no move or join: a recording killed unpaused (Kanade's crash or SIGTERM included, the recorder dying by SIGINT with it) leaves a playable file at its name. The segments after a pause are `002.mp4`... in a hidden sibling folder `.Screencast from <stamp>.parts/` of the final file. Stop, after a resume, moves the first segment into that folder as `001.mp4`, joins them with `ffmpeg -f concat -safe 0 -c copy` (the list is relative to its own folder, names single-quoted) and moves the joined file to the final name. Stop of a recording paused and not resumed has nothing to join: the file is the recording already. `ffmpeg` is needed only to pause: without it a start works and pause is refused, saying why.
- **A move never replaces.** Both moves use `RENAME_NOREPLACE` (a plain rename where the filesystem has none, after a look for the name). A file that appeared at the final name meanwhile is left as it is: the join's result and the segments stay in the folder and the Failed Activity names them. If the join fails, the first segment is put back at the final name when that is still free.
- **Only what Kanade made is deleted, and only on success.** After a successful save the segments, the list, the joined file and the then-empty folder are removed, never the folder as a whole. An empty file `wf-recorder` left (it writes nothing before the screen changes, and a stop before that is an empty segment, not a failure) is deleted at once, as the then-empty folder is: what a failure keeps is named only if it holds footage. If joining fails or times out (600 s) the segments are kept and the Failed Activity names the folder. A recording resumed and then killed, or one whose join Kanade did not survive, leaves the file with the first segment and a `.parts` folder with the rest (or, when the death came during the join, no file at the final name and every segment in the folder): Kanade never deletes the folder (the segments are all the user has), and the wiki says so. The final name is chosen so that neither the file nor the folder collides with a taken one.
- **Locking stops and saves.** While a recording runs, a session lock (`request_lock`) feeds a lock event to the machine, which stops and saves, from Paused too; a start or resume is refused while `lock::holds()`. The hook only reads an atomic flag and spawns a short thread, so the lock path never waits on the recording's lock; `lock::holds()` is never called under the recording's lock (lock order), and a start or resume that succeeded re-checks it once, to close the race. ADR 0111's note about audio recorded just before a lock is a separate matter.
- **Everything is spawned from one long-lived worker thread.** `setpriv --pdeathsig` is tied to the thread that spawned the child, not the process, so a short-lived thread would kill the recorder when it ended (the dictation's gate follows the same rule, ADR 0011). The worker runs `slurp` (a stream holder, killed with Kanade), each `wf-recorder` segment (a file holder, INT) and `ffmpeg` (bounded). A follower thread per child waits for it and feeds its end back; the child is stored with the machine and reaped under its lock.
- **No polling.** The Arbiter reads no clock and `island/` names no `kanade_runtime`. The one 50 ms check is a frame watcher thread alive only while a `start` or `resume` request is open, which answers the CLI with the path once the recorder writes its first frame (the file appears only then), bounded by the 5 s of the open reply. Views read only the island (the Activity's `Clip::Recording` carries the path, the audio, paused, and whether it can pause), never the machine.
- **The verb.** `capture record start [screen|area [<x,y WxH>]|window [<id>]] [none|system|mic|both|mix]`, `pause`, `resume`, `stop`, `status`. `start` answers once the first frame is written, and `stop` once saved or failed, up to the usual 5 s (a long join can answer unknown; the file still lands). The Activity shows Pause (or Resume) and Stop; while the segments are joined (up to 600 s) it says Saving and offers neither (`Clip::Saving`); a paused recording shows a Pause icon in its Satellite. The Capture Surface has the Record tile, a Rec Area pill, the audio pill (it cycles none -> system -> mic -> mix -> none) and, while recording, Pause or Resume.
- **Privacy is unchanged.** Every segment goes through niri's wlr-screencopy, damage tracked (never `-D`), so the privacy cluster counts it as a cast, and the microphone indicator shows a recorded microphone. Nothing hides a pause: between segments no cast shows because none runs.

## Alternatives

**Pausing the one `wf-recorder` with SIGSTOP.** The stream stays open and niri still lists the cast, so the cluster would show a recording that records nothing, and the file's timestamps would still run on.

**A window target now.** Needs a PipeWire cast of the window and a pipeline in Kanade or a D-Bus portal prompt each time; deferred, with `slurp` for an area meanwhile.

**Kanade's own region overlay in place of `slurp`.** A coherent runtime primitive, but one more surface to build for what `slurp` does; later.

**A microphone default in config.** A persisted default would record the user's voice without them choosing it on that start; refused.

**Concatenating with a re-encode.** Copies cost nothing and keep the GPU's encode; a segment started later has its own timestamps, which the demuxer offsets.

## Consequences

- `slurp` (for an area) and `ffmpeg` (for a pause) are optional dependencies, named by `doctor`-style errors at use and in the docs; `wf-recorder` and VA-API remain required.
- The file is there from the first frame and, never paused, is the finished recording at Stop. A recording resumed after a pause has only its first segment at the final name until Stop, which moves it into the hidden folder for the join (the final name is absent for that join, up to 600 s) and writes the whole to the final name; a crash before the move leaves the file with the first segment and the folder with the rest, and one during the join or the last move leaves the final name absent and every segment (001 included, and maybe a partial `.joined.mp4`) in the folder (documented, not auto-deleted).
- Each resumed segment pays the recorder's first-frame delay, so a still screen's gap after a resume is short but real.
- Unverified until run on a session: that `wf-recorder` takes the `@DEFAULT_MONITOR@` and `@DEFAULT_SOURCE@` names, that `slurp` runs with a null stdin, and the audio and video sync across joined segments.
- `start` of a screen or a given area prints the final path once the first frame is written, and the file exists then (unpaused it stays, and is the recording; after a resume it is replaced by the whole at Stop). `start` that has the user draw the area prints no path (the area is not chosen yet); `stop` prints the path once the recording is saved there.
- A failed screenshot shows a Failed Activity, "Screenshot failed" (`live::screenshot_failed`), as the island is already closed by then; the detail puts the cause first, since it is cut to a line. A request niri may or may not have taken (`Asked::Unknown`) posts nothing, on purpose: the screenshot may still be saved. A screenshot niri says it saved (`ScreenshotCaptured`) shows on the focused output for a while, the path as the title, or "Copied" when niri kept no path; no thumbnail, and the path is not logged. That includes a screenshot Kanade did not ask for.
- A failed start shows a Failed Activity that preempts what the island shows (the picker failing, `slurp` missing, a recorder that cannot start: the user just acted); a picker the user leaves shows nothing. A failure that comes later, from a join or a recording that ends on its own, shows without preempting, so it never collapses a Surface the user is typing in. When a join finds its name taken, the Failed Activity says so and names only the folder, as the file there is not Kanade's.
- The Launcher shows Start and Record Area only while no recording runs, Pause while one runs and can pause, Resume while paused, and Stop in any state of one (the closed table of ADR 0112 is unchanged; its rows are filtered by the recording's standing as the island holds it). The set is recomputed on each fit, key, wheel and render, from the standing the island holds, so it is stale at most one frame.

## Update: encoder choice and quality

Recordings looked poor: `wf-recorder`'s defaults gave VA-API's rate control a default quality and converted the screen to full-range YUV with an untagged matrix, which players read as BT.709 and show with shifted colors (a measured SSIM of 0.50 against the source, 0.91 after the fix below); the window path used `vah264enc`'s default rate control the same way. Still H.264 and still damage tracked (variable frame rate, no `-D`); `wf-recorder`, `gst-launch-1.0` and `ffmpeg -c copy` into the mp4 stay.

- **Constant quantizer.** `recording.quality` (`low`, `medium`, `high` default, `max`) is one choice for every encoder: VA-API `rc_mode=CQP` with `qp` 26, 23, 20, 16; NVENC `rc=constqp` with the same qp; libx264 `crf` 27, 23, 19, 15. A fixed quantizer keeps the picture's quality whatever it does, a still screen costs nothing and a busy one what it needs. Measured with a 5 s 1080p30 test pattern of text over moving bars (Mbit/s; SSIM of the text region): VA-API qp 20 15.4 (0.888), qp 16 20.1 (0.904), qp 24 11.6 (0.821); libx264 veryfast crf 19 9.9 (0.894); NVENC constqp 19 15.1 (0.894). VA-API's own default (ICQ 20) gave 12.6 (0.881), `-bf 2` and `-quality 1` changed nothing, a bitrate cap (VBR 8 Mbit/s) 8.3. A quality step is 3 to 4 quantizer values and changes the size of a busy picture by 25 to 30% (VA-API qp 24, 20, 16: 11.6, 15.4, 20.1 Mbit/s); below 20 it grows fast for little to see, above 24 text smears.
- **Color.** The encoder is fed BT.709 limited range through `-F` (`scale_vaapi=format=nv12:out_range=tv:out_color_matrix=bt709...`, or `scale` and `yuv420p` for the CPU), and tagged so in the H.264 headers (video usability information: primaries, transfer, matrix, range) by the encoder itself: `wf-recorder -p colorspace=bt709 -p color_primaries=bt709 -p color_trc=bt709 -p color_range=tv` for all three encoders. The `out_color_*` options of `scale_vaapi` only describe the frames to the filter graph, no encoder reads them; without the `-p` tags h264_vaapi writes no color tag at all and a player takes a picture under 720 lines as BT.601. Checked with libavcodec given the same options through the dictionary `wf-recorder -p` fills, with the headers read back (`trace_headers`): h264_vaapi, h264_nvenc and libx264 each write BT.709 limited. A window's stream, from GStreamer, is tagged by `ffmpeg`'s `h264_metadata` bitstream filter as it is copied into the mp4. Not yet seen through a live `wf-recorder` capture; a recording is tagged only if `wf-recorder` passes `-p` to the encoder as its source reads.
- **Encoder choice, `recording.encoder`.** `auto` (default), `vaapi`, `nvenc` or `software`. `auto` takes the first that encodes a real frame: VA-API on an Intel or AMD render node (the one that drives the display first; never an NVIDIA node), then NVENC, then libx264 (`veryfast`, up to 4 threads, `yuv420p`). NVENC is not tried while VA-API works, so the NVIDIA GPU of a hybrid machine is not woken. A named encoder that does not work gives way to software and says so. The probe is one frame through `ffmpeg` (a lavfi test source, a 10 s limit, that it works is kept for the run, that it failed for a minute, a trial that overran or could not run not at all, and `kanade doctor` and Settings Health always try afresh) in `probe.rs`; the choice is pure (`encode.rs`: vendor from `/sys/class/drm/*/device/vendor`, order, arguments), the probe behind a trait. `recording.device` names the render node VA-API uses (only `/dev/dri/renderD` and a number is accepted; unset finds one). `-d <node>` pins it in `wf-recorder`; a window's GStreamer encoder is `vah264enc` for the first non-NVIDIA node and `va<node>h264enc` (`varenderD129h264enc`) for the rest, with the post-processor of the same node (`vapostproc`, `varenderD129postproc`) so that both share a display. A recording keeps the settings it began with, so a reload of the config between a pause and the resume changes nothing within one file.
- **Window path.** `vapostproc` (the node's own, see above) with `vah264enc rate-control=cqp`, or, for NVENC and x264, `vapostproc` to system memory (else `glupload ! gldownload ! video/x-raw ! videoconvertscale`, where no VA-API driver works) with `nvh264enc rc-mode=constqp` or with `x264enc pass=quant` (`pass=qual` ignores the quantizer), each probed through `gst-launch-1.0` first; the caps name BT.709. niri casts DMA-BUF, including compressed tiled buffers, which `vapostproc` imports and a CPU converter or EGL may not ([ADR 0117](0117-window-recording-through-nirs-screen-cast.md), Update).
- **A start that fails falls back once.** A segment whose encoder ended without writing a frame (and is not software, and is not a missing program) is started again with libx264, said on stderr and in the status ("software encoding"). This supersedes ADR 0013's "no fallback encoder": the choice is stated and shown (`kanade doctor` reports the chosen encoder, its node, why and what is missing), not silent, and it is made once per recording. A recording on a broken GPU setup no longer fails, it costs CPU; the cause is in the log.
- **Not verified through `wf-recorder`:** its `-F` replacing the default filter, `-p rc_mode=CQP -p qp=N` and the color `-p` tags reaching the encoder, `-d`, the `va<node>` element names on a second VA-API node (only one exists here), and NVENC and software under `wf-recorder`, as capturing the screen is not testable without recording the user's session. The equivalent `ffmpeg` and GStreamer chains were measured on synthetic sources. A live check is listed in `TODO.md`.

## Update: system and microphone audio mix

Simultaneous system and microphone audio capture is supported (`both` or `mix`), superseding the earlier single-source limitation. PulseAudio / PipeWire loads a virtual null sink (`module-null-sink sink_name=kanade-record-mix sink_properties=device.description=KanadeRecordMix`) and two loopbacks (`module-loopback source=@DEFAULT_MONITOR@ sink=kanade-record-mix latency_msec=20` and `module-loopback source=@DEFAULT_SOURCE@ sink=kanade-record-mix latency_msec=20`). Both `wf-recorder` (screen/area) and `ffmpeg` (window) capture from `kanade-record-mix.monitor`. Lifecycle cleanup unloads the modules in reverse order upon recording stop, failure, or process drop, tracked via `$XDG_RUNTIME_DIR/kanade/pulse-mix.<pid>`. Shell startup reclaims dead ledgers and lingering mix modules.
