# 117. Window recording through niri's screen cast

Status: accepted (Capture, slice 2). Completes [ADR 0116](0116-recording-targets-audio-and-pause.md), which left a window target out: the state machine, segments, pause, join, audio choice and lock rule of 0116 apply to it unchanged. Builds on ADR 0011 (holders) and ADR 0112 (the Launcher's closed verbs).

## Context

niri gives no rectangle for a tiled window (its layout scrolls), so `wf-recorder -g` cannot record one. niri does implement `org.gnome.Mutter.ScreenCast` on the session bus, and its `RecordWindow` casts one window by its niri id, with no portal prompt. A spike on the user's session found: `CreateSession`, `RecordWindow({"window-id": u64})` and `Start` answer OK even for an id that is not open; the failure shows only as no cast for the session in `niri msg --json casts`. The cast has a `pw_node_id`, and its `pid` is null (the caller is not a process niri knows).

## Decision

- **Target `window [<id>]`.** `kanade capture record start window [<id>] [none|system|mic]`. Without an id it is the focused window at start. The recording keeps the id, not the title; a window that is not open is refused at start (`window N is not open`), as is no focused window. The Capture Surface has a `Rec Window` pill and the Launcher a `Record Window` row (record only; the Launcher still denies `mic`, ADR 0112).
- **Cast.** Kanade calls `CreateSession`, `RecordWindow` and `Start` on its own zbus session connection. After a short wait it looks for the session in niri's casts: none means niri would not cast the window (gone), reported as such. The cast's `pw_node_id` is the PipeWire node to read.
- **Pipeline.** `gst-launch-1.0 pipewiresrc path=<node> ! vapostproc add-borders=true ! video/x-raw(memory:VAMemory),width=W,height=H ! vah264enc ! h264parse ! fdsink`, piped into `ffmpeg -f h264 -i - [audio input] -c:v copy -fps_mode vfr FILE`. `W,H` are the window's size at start, rounded down to even and fixed for the recording: a window resized later is letterboxed to the first size, not rescaled to another size. The encoder is on the GPU (VA-API), as in 0013, with no fallback.
- **Why ffmpeg stamps by wall clock.** `pipewiresrc ! mp4mux` gave every frame the same PTS in the spike (the cast stamps no usable times). ffmpeg reads the raw H.264 with `-use_wallclock_as_timestamps 1`, so a frame's time is when it arrived, and a still window records few frames (variable frame rate, as with `wf-recorder`). The audio input is stamped the same way and the file ends with the video (`-shortest`; the audio never ends of itself). **A/V sync is not guaranteed**: it is as good as the encoder's latency is steady, and is not corrected. ffmpeg probes the raw stream briefly (`-probesize 65536 -analyzeduration 1`) so the file appears within `start`'s 5 s. The mp4 is fragmented (`-movflags +frag_keyframe+empty_moov+default_base_moof`, `-frag_duration 1000000`, `-flush_packets 1`) so a writer killed with Kanade (`--pdeathsig`) leaves a file playable up to its last fragment: a plain mp4 has no `moov` until the end (a `kill -9` left 48 bytes, `moov atom not found`). The fragment is cut each second and not only at a keyframe because a still window has long gaps between keyframes (with `frag_keyframe` alone the killed file held nothing for a long GOP); `flush_packets` is needed because a small stream otherwise stays in ffmpeg's 32 KiB output buffer and a killed writer leaves only the header. The join (0116) copies these into a normal mp4 (`moov` at the end, no fragments).
- **Segments.** One pipeline (writer ffmpeg, encoder gst) and one cast per segment; pausing ends the segment and resuming casts the window again. Interrupting SIGINTs the encoder, which ends the writer by EOF; the writer is the follower's wait, the session is stopped after both ended. `setpriv --pdeathsig` ties both to the spawning worker thread, so the pipeline dies with Kanade.
- **A window that closes.** If the encoder fails and PipeWire says the target is not found (or niri no longer lists the window), the segment ended on its own as written, not as failed: the machine joins and saves what exists, and the Clip says `Saved, window closed`. Closing while Paused hears niri's window-closed event and saves the same way. A start whose window closed before the first frame is a failure, with the segment's reason.
- **Leaks.** niri does not stop a session when its D-Bus client dies, and a cast that stays shows as a live screen cast. Kanade stops the session on every end path, remembers its sessions in its own file `$XDG_RUNTIME_DIR/kanade/window-casts.<pid>` (one `<NIRI_SOCKET>\t<session>` line each; no two Kanades share a file), forgets one only once niri's casts no longer list it (a session that stays is kept for a later start), and at startup stops only the casts named in the files of Kanades that are gone (their pid does not run as a process of the same name) that are still casts of a Window with a null pid, through niri's `stop-cast`; one that cannot be stopped, or whose niri cannot be asked, stays in its file. A cast of another program, one of a Kanade that runs, or one this run made, is never touched. A stop with no frame written ends the segment as empty whatever the writer says; an encoder that does not end after a stop is killed after 5 s, and the writer 5 s later, so the cast and the dot do not stay up. Kanade has no shutdown hook, so a graceful exit during a recording relies on this reclaim at its next start (the pipeline itself dies with it).
- **Privacy.** The cast is a screen cast with a null pid, so the privacy cluster shows it. It is shown beside the Recording Clip, not deduplicated against it; see `TODO.md`.
- **Doctor.** Recording a window needs `gst-launch-1.0` (with `pipewiresrc`, `vapostproc` and `vah264enc`: gst-plugin-pipewire, gst-plugins-bad) and `ffmpeg`; `kanade doctor` lists both.

## Alternatives

- **`pipewiresrc ! mp4mux` in GStreamer alone.** Constant PTS in the spike; no wall-clock option.
- **`wf-recorder -g` on a computed rectangle.** niri gives none for a tiled window, and it would record what overlaps it.
- **The xdg-desktop-portal ScreenCast.** Prompts for each start; the Mutter interface does not.
- **Rescaling on resize.** A new size mid-file breaks a stream copy and the join of segments; a fixed size letterboxes.

## Consequences

- Checked headless on the encoder pipeline alone (synthetic x264 source piped into the same ffmpeg arguments, writer `kill -9`: a file that ffprobe reads and ffmpeg decodes, about a second short; the same with audio; a graceful end seekable; two fragmented segments joined by `-f concat -c copy` into a normal mp4, with and without AAC audio). NOT live-verified: a `kill -9` of Kanade during a real window recording (gst's `vah264enc` stream, the real cadence and keyframe interval), until Iris reruns it.
- `gst-launch-1.0` and its plugins become dependencies of window recording only; screen and area recording are unchanged.
- Verified live on a kitty window: start, pause, resume, stop (joined), a window closed while recording and while paused (saved), a stale session reclaimed after `kill -9` (against the old shared ledger, before the per-pid ledger), system sound. NOT live-verified (the review's fixes too): the per-pid ledger's `kill -9` reclaim, the watchdog killing a stuck encoder, the post-open check, a stop with no frame written, niri's Stop sharing on a window cast (the cast ends; whether the recording is saved is unknown, and the code treats an encoder that dies on it as a failure unless the window closed), a lock during a window cast, microphone sound, a HiDPI window (the size is niri's logical size, which a scaled output may not match), A/V sync, a window that resizes, the Capture Surface's Rec Window pill and the Launcher's Record Window row, a second Kanade starting beside a window recording.
