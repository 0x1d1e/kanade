# 117. Window recording through niri's screen cast

Status: accepted (Capture, slice 2). Completes [ADR 0116](0116-recording-targets-audio-and-pause.md), which left a window target out: the state machine, segments, pause, join, audio choice and lock rule of 0116 apply to it unchanged. Builds on ADR 0011 (holders) and ADR 0112 (the Launcher's closed verbs).

## Context

niri gives no rectangle for a tiled window (its layout scrolls), so `wf-recorder -g` cannot record one. niri does implement `org.gnome.Mutter.ScreenCast` on the session bus, and its `RecordWindow` casts one window by its niri id, with no portal prompt. A spike on the user's session found: `CreateSession`, `RecordWindow({"window-id": u64})` and `Start` answer OK even for an id that is not open; the failure shows only as no cast for the session in `niri msg --json casts`. The cast has a `pw_node_id`, and its `pid` is null (the caller is not a process niri knows).

## Decision

- **Target `window [<id>]`.** `kanade capture record start window [<id>] [none|system|mic]`. Without an id it is the focused window at start. The recording keeps the id, not the title; a window that is not open is refused at start (`window N is not open`), as is no focused window. The Capture Surface has a `Rec Window` pill and the Launcher a `Record Window` row (record only; the Launcher still denies `mic`, ADR 0112).
- **Cast.** Kanade calls `CreateSession`, `RecordWindow` and `Start` on its own zbus session connection. After a short wait it looks for the session in niri's casts: none means niri would not cast the window (gone), reported as such. The cast's `pw_node_id` is the PipeWire node to read.
- **Pipeline.** `gst-launch-1.0 pipewiresrc path=<node> ! vapostproc add-borders=true ! video/x-raw(memory:VAMemory),width=W,height=H ! vah264enc ! h264parse ! fdsink`, piped into `ffmpeg -f h264 -i - [audio input] -c:v copy -fps_mode vfr FILE`. `W,H` are the window's size at start, rounded down to even and fixed for the recording: a window resized later is letterboxed to the first size, not rescaled to another size. The encoder is on the GPU (VA-API), as in 0013, with no fallback.
- **Why ffmpeg stamps by wall clock.** `pipewiresrc ! mp4mux` gave every frame the same PTS in the spike (the cast stamps no usable times). ffmpeg reads the raw H.264 with `-use_wallclock_as_timestamps 1`, so a frame's time is when it arrived, and a still window records few frames (variable frame rate, as with `wf-recorder`). The audio input is stamped the same way and the file ends with the video (`-shortest`; the audio never ends of itself). **A/V sync is not guaranteed**: it is as good as the encoder's latency is steady, and is not corrected. ffmpeg probes the raw stream briefly (`-probesize 65536 -analyzeduration 1`) so the file appears within `start`'s 5 s. The mp4 is fragmented (`-movflags +frag_keyframe+empty_moov+default_base_moof`, `-frag_duration 1000000`, `-flush_packets 1`) so a writer killed with Kanade (`--pdeathsig`) leaves a file playable up to its last fragment: a plain mp4 has no `moov` until the end (a `kill -9` left 48 bytes, `moov atom not found`). The fragment is cut each second and not only at a keyframe because a still window has long gaps between keyframes (with `frag_keyframe` alone the killed file held nothing for a long GOP); `flush_packets` is needed because a small stream otherwise stays in ffmpeg's 32 KiB output buffer and a killed writer leaves only the header. The join (0116) copies these into a normal mp4 (`moov` at the end, no fragments).
- **No `videorate`: the frames keep their own rate.** The chain is `pipewiresrc path=<node> keepalive-time=1000 resend-last=true ! video/x-raw(ANY),pixel-aspect-ratio=1/1 ! <encoding chain> ! h264parse ! fdsink`, with nothing between the cast and the encoder that fixes a framerate. The wall clock is what gives the take its duration: `keepalive-time`/`resend-last` make a still window re-emit its last buffer each second, and every buffer is stamped on arrival. A source whose framerate is **not fixed** (niri's cast carries none, and `pipewiresrc` offers none) must never be piped through `videorate`: it passes a single frame and then bursts the rest at `stop`. See the last update.
- **Segments.** One pipeline (writer ffmpeg, encoder gst) and one cast per segment; pausing ends the segment and resuming casts the window again. Interrupting SIGINTs the encoder, which ends the writer by EOF; the writer is the follower's wait, the session is stopped after both ended. `setpriv --pdeathsig` ties both to the spawning worker thread, so the pipeline dies with Kanade.
- **A window that closes.** If the encoder fails and niri no longer lists the window, the segment ended on its own as written, not as failed: the machine joins and saves what exists, and the Clip says `Saved, window closed`. Closing while Paused hears niri's window-closed event and saves the same way. A start whose window closed before the first frame is a failure, with the segment's reason.
- **Leaks.** niri does not stop a session when its D-Bus client dies, and a cast that stays shows as a live screen cast. Kanade stops the session on every end path, remembers its sessions in its own file `$XDG_RUNTIME_DIR/kanade/window-casts.<pid>` (one `<NIRI_SOCKET>\t<session>` line each; no two Kanades share a file), forgets one only once niri's casts no longer list it (a session that stays is kept for a later start), and at startup stops only the casts named in the files of Kanades that are gone (their pid does not run as a process of the same name) that are still casts of a Window with a null pid, through niri's `stop-cast`; one that cannot be stopped, or whose niri cannot be asked, stays in its file. A cast of another program, one of a Kanade that runs, or one this run made, is never touched. A stop with no frame written ends the segment as empty when the writer succeeds or reports no stream; an encoder that does not end after a stop is killed after 5 s, and the writer 5 s later, so the cast and the dot do not stay up. Kanade stops its held cast on graceful exit, and a crash relies on this reclaim at its next start (the pipeline itself dies with it).
- **Privacy.** The cast is a screen cast with a null pid, but matched against Kanade's ledger of own window-cast sessions so it is recognised as Kanade's own and does not show in the privacy cluster beside the Recording Clip.
- **Doctor.** Recording a window needs `gst-launch-1.0` (with `pipewiresrc`, `vapostproc` and `vah264enc`: gst-plugin-pipewire, gst-plugins-bad) and `ffmpeg`; `kanade doctor` lists both.

## Alternatives

- **`pipewiresrc ! mp4mux` in GStreamer alone.** Constant PTS in the spike; no wall-clock option.
- **`wf-recorder -g` on a computed rectangle.** niri gives none for a tiled window, and it would record what overlaps it.
- **The xdg-desktop-portal ScreenCast.** Prompts for each start; the Mutter interface does not.
- **Rescaling on resize.** A new size mid-file breaks a stream copy and the join of segments; a fixed size letterboxes.

## Consequences

- Checked headless on the encoder pipeline alone (synthetic x264 source piped into the same ffmpeg arguments, writer `kill -9`: a file that ffprobe reads and ffmpeg decodes, about a second short; the same with audio; a graceful end seekable; two fragmented segments joined by `-f concat -c copy` into a normal mp4, with and without AAC audio). NOT live-verified: a `kill -9` of Kanade during a real window recording (gst's `vah264enc` stream, the real cadence and keyframe interval), until Iris reruns it.
- `gst-launch-1.0` and its plugins become dependencies of window recording only; screen and area recording are unchanged.
- Verified live on a kitty window: start, pause, resume, stop (joined), a window closed while recording and while paused (saved), a stale session reclaimed after `kill -9` (against the old shared ledger, before the per-pid ledger), system sound. NOT live-verified (the review's fixes too): the per-pid ledger's `kill -9` reclaim, the watchdog killing a stuck encoder, the post-open check, a stop with no frame written, niri's Stop sharing on a window cast (the cast ends; whether the recording is saved is unknown, and the code treats an encoder that dies on it as a failure unless the window closed), a lock during a window cast, microphone sound, a HiDPI window (the size is niri's logical size, which a scaled output may not match), A/V sync, a window that resizes, the Capture Surface's Rec Window pill and the Launcher's Record Window row, a second Kanade starting beside a window recording.

## Update: the encoders that run on the CPU's frames

Window recording worked only with VA-API (Iris, live, niri 26.04): with `software` and `nvenc` the pipeline ended with `no more input formats` from `pipewiresrc` and `not-negotiated (-4)`. **Cause:** niri 26.04 casts DMA-BUF only, with a mandatory modifier list (`pw_utils.rs`: `make_video_params` offers no plain format; the shared-memory fallback came to its main branch after the 26.04 tag), and `pipewiresrc` offers the formats the element after it can take. `vapostproc` takes DMA-BUF; `videoconvertscale`, which fed `x264enc` and `nvh264enc`, does not, so nothing was left to offer. Reproduced here with a small program that casts as niri does (a DMA-BUF-only node with the fixating modifier handshake, buffers from GBM, nothing of the user's windows): `pipewiresrc ! videoconvertscale ! x264enc` fails with the same two messages, and `pipewiresrc ! vapostproc ! vah264enc` encodes.

- **Window path for NVENC and x264, first try (98d6b43), which failed live.** `pipewiresrc ! glupload ! gldownload ! video/x-raw ! videoconvertscale ! <caps> ! nvh264enc | x264enc` negotiated, but the first buffer failed: the cast's modifier was `0x0100000000000008` (Intel's `Y_TILED_GEN12_RC_CCS_CC`, compressed and tiled, three planes) and Mesa's EGL refuses to import it (`eglCreateImage failed: EGL_BAD_MATCH`, `Failed to upload buffer`, "Indirect uploads are only support for linear formats", stream error -5). The first stand-in offered only linear and plain tiled modifiers (`0`, `I915 X`, `Y`), which `glupload` imports, so it passed. Now the stand-in offers the set niri builds (the render formats of its EGL context: linear, X, Y, `Y_TILED_GEN12_RC_CCS` and `RC_CCS_CC`, those GBM on renderD128 can allocate), allocates three-plane buffers and fixates as niri does: it picks `...08`, and `glupload` fails with `Failed to upload buffer` as live (with a linear-only offer it passes).
- **Window path for NVENC and x264, now.** The frames come from the VA-API post-processor, which imports that buffer: `pipewiresrc ! vapostproc add-borders=true ! video/x-raw,width=W,height=H,format=I420|NV12,colorimetry=bt709 ! x264enc | nvh264enc` (the node's own `va<node>postproc`, see 0116). It converts, scales and letterboxes on the way, so no `videoconvertscale` follows. It needs a VA-API driver (Intel or AMD); the GPU does the download and conversion, the encoder is still NVENC or x264. Where none works (an NVIDIA-only machine, an AMD one without the driver) the chain falls back to `glupload ! gldownload ! video/x-raw ! videoconvertscale ...` (`Download::Gl`), which needs no VA-API but **cannot import a compressed tiled buffer**: whether it works there depends on the modifier niri's GPU offers, which is not verified for NVIDIA or AMD. Honest requirement: window recording with NVENC or x264 is verified only where VA-API works; elsewhere it is unverified and may fail at the first buffer, as the first try did. All the chains, VA-API's too, encoded 100 or more frames of the stand-in cast through `ffmpeg`'s `h264_metadata` into an mp4 that ffprobe reads as H.264, BT.709 limited.
- **Choosing the download.** `probe::window` tries the whole chain through `gst-launch-1.0` with the `vapostproc` of each node VA-API may use (the Intel and AMD nodes, the primary display's first; `recording.device` if set), then the EGL one, and keeps the first that encodes a test frame (the cache and time limit of the other trials apply). The choice is by this trial and not by the `ffmpeg` VA-API probe, since GStreamer's VA plugin is what runs.
- **Doctor and the trial.** `gst_trial` runs the chosen chain on a test pattern in system memory, so it cannot see a live cast's DMA-BUF or its tiling: it catches a missing element, a missing VA-API driver or no EGL. `kanade doctor` (and Settings Health) asks afresh and adds a `window:` line to the recording check naming the download used ("frames downloaded through VA-API on /dev/dri/renderD128 (vapostproc)" or "EGL (glupload)") and saying "a live cast is not tried"; a failure makes the check a warning (screen and area recording are unaffected).
- **A failed live download gives way at run time.** The trial cannot see a wrong-GPU or tiling failure of the live cast (the cast may be allocated by another GPU than the Intel or AMD node that encodes a test frame, as with an AMD boot GPU and an NVIDIA GPU that renders), and its `Works` is kept for the process. So a window segment that used the VA-API download (`Download::Va`) and ends before it wrote a frame, with the encoder (not the muxer) to blame, sets `no_va` on the take: the segment starts again with EGL for the download, the same encoder, and `probe::window` tries no VA node for that encoder (`encode::downloads`, unit-tested to return EGL only). If that fails too, an encoder that is not software starts again with software (ADR 0116), which clears `no_va`: the encoder may have failed for its own reasons (NVENC's session limit, a driver), and software with the VA-API download can work where EGL cannot import the cast. If software with VA-API fails, it takes EGL once more, and then the recording fails. Each step is taken once (`again`, unit-tested: at most three restarts, VA-API to EGL, hardware to software, VA-API to EGL), so nothing loops. A muxer failure skips the EGL step, since the download is not to blame. The next recording tries VA-API again.
- **Not yet verified:** a window resized during a recording on niri's own cast (Iris is running it); machines without VA-API (NVIDIA-only, AMD without the driver) and the EGL path there; hybrid topologies (the live fallback from VA-API to EGL has not run on a real hybrid machine; its choice is unit-tested).
- **A resize letterboxes (`pixel-aspect-ratio=1/1`, twice).** Live (Iris, at d507a1a), a window resized during a recording kept the file's size but its picture was stretched, not bordered, on all three encoders, in spite of `add-borders=true` and a `pixel-aspect-ratio=1/1` on the output caps; `GST_DEBUG` showed `vapostproc: Can't calculate borders` at the start and at the resize. Reproduced with the stand-in made to renegotiate as niri does (a fresh `EnumFormat` with the new size through `update_params`, the modifier fixation again, new buffers): the log shows that the input caps `vapostproc` is given are `video/x-raw(memory:DMABuf), drm-format=AR24:..., width=800, height=500, pixel-aspect-ratio=1/2147483647`. The cast says no pixel aspect, and `pipewiresrc` leaves the range's lower bound in the caps; with that aspect `gst_va_vpp_set_info` cannot calculate the borders and scales to fill. The output caps' `pixel-aspect-ratio=1/1` (the earlier fix, which a synthetic caps change did pass) is still right but was not the cause. Fix: the cast is held to square pixels, `pipewiresrc ! video/x-raw(ANY),pixel-aspect-ratio=1/1 ! <chain>` (`ANY` since the memory is DMA-BUF, or system memory should niri one day offer SHM). Checked on the renegotiating stand-in, white 400x500 frames resized to 800x500 and to 250x500, reading the rows and columns of the last frame: VA-API, NVENC and x264 through `vapostproc`, and both through EGL (linear modifier only, as it imports no more), all give a centred white band of 250 rows (or of 250 columns) and black bars; without the filter the white fills the frame. A static window is unchanged. Not run against niri's own resize (Iris).

## Update: `videorate` was added back and broke every window recording

`fae1e04` put `videorate ! video/x-raw(ANY),framerate=30/1` between the square-pixel caps and the encoding chain, to pace a still window to a steady 30 fps, and this ADR was not amended. It did the opposite of what the decision above says, and of what it was added for.

- **What it did.** `pipewiresrc` offers **no fixed framerate** (niri's cast carries none, and nothing fixated one before the element). Fed caps that fix none, `videorate` emits a single frame and holds its input: it passed about one frame per take, then flushed the rest in a burst at `stop`. Live (Iris), three takes: 729/1489/1460 frames in files of 2.45/5.02/5.02 s, a file rate of 291-297 fps against ~27 fps of real content, and nothing on disk during the recording. `start` then always hit its 5 s budget (the window path wrote no file until the muxer finished), and a `kill -9` left no footage at all. Reproduced in the lab, 10 s each: `videotestsrc is-live=true ! video/x-raw,framerate=0/1 ! videorate ! video/x-raw,framerate=30/1 ! fdsink` gave 614 KB, **one frame**; the same source without `videorate`, 221 MB; with a fixed `30/1` input into `videorate`, 184 MB. `videorate` is not wrong in itself, only the caps it was given.
- **Decision: no pacing element, and a source whose framerate is not fixed MUST NOT go through `videorate`.** The chain is the one in the decision above, unchanged: square pixels, then the encoding chain, then `h264parse`. The still-window case `videorate` was added for is already answered by `keepalive-time=1000` with `resend-last=true` (a still window re-emits its last buffer each second) and by `-use_wallclock_as_timestamps 1` in the muxer, which turns those buffers into the duration the take really had. A still window therefore records few frames over a correct duration, which is VFR working as decided, not a defect to be paced away. `plan::encoder`'s argument list asserts both the square-pixel caps and the absence of `videorate` and of any `framerate=` caps, so the element cannot come back unnoticed.
- **Verified live (Felix, at `03ad9a2`).** An animated window and a still window, each recorded for more than 20 s of wall time through niri's cast: duration, frame count and playability are in the commit's report; the still window kept a duration close to its wall time with a handful of frames.
